# 客户负责人/当前账期负责人自定义规格创建与底槽识别修复报告

日期：2026-09-22。状态：本地代码、自动测试与原生编译完成；未部署、未上传、未提交 Git。

本轮只开放负责客户业务中的自定义规格创建，并修复“底槽”产品身份。普通成员没有获得全局产品管理、修改或启停权限。产品继续保存在企业共享库，价格、单位换算、账务、历史快照、导出及 GC 规则保持。

## 一、原权限与调用链

**1. 原 createCustomProduct 权限位置。** `cloudfunctions/ledger/index.js` 的 `ADMIN_MUTATIONS` 包含该 action；`cloudfunctions/ledger/services/member-security.js` 的 `MEMBER_MUTATIONS` 不包含它，`assertMutationPermission` 对普通成员返回“当前操作仅限管理员”。原领域仓储的 `createCustomProduct` 只有确认、名称、重复检测和写入，没有负责客户范围授权。

**2. 原快速记账调用链。** `parseOrderText` 返回未匹配行及 `customProductDraft` → 行内创建按钮或产品选择器 → `openCustomProductForm` → 用户编辑并点击“保存并使用” → `saveCustomProduct` → `services/cloud-repository.js.createCustomProduct` → `ledger main` → `mutate` → 事务中的领域 `createCustomProduct` → 内容安全 → 持久化 → 返回产品 → `finishCustomProductSave/applyProductSelection` 为当前行设置 productId。另一个创建入口是管理员 `pages/product-form` 新建表单。全项目搜索未发现其他生产创建入口。

原解析结果中的 `canCreateCustomProduct` 只表示“产品尚不存在”，不是用户权限；本轮另外增加 `canCreateForClient` 控制 UI。原“我的”页产品管理菜单已经仅管理员可见，本轮补齐直接进入产品页/表单的页面守卫。

## 二、最终创建权限与安全边界

**4. 最终表达式。** 前置条件是服务端真实 active membership；普通成员分支还必须有当前企业的真实业务客户。

```text
membership.role === 'admin'
OR membership.id === client.ownerMemberId
OR membership.id === uniqueCurrentOpenPeriod.ownerMemberId
```

实现为独立 `canCreateCustomProduct`，不改变 `canManageCustomerPrices`、`canEditShipment` 或 `canCloseBillingPeriod`。管理员保留无需客户上下文的全局创建能力。

**5. client owner 校验。** 普通成员请求必须提供非空 clientId。云事务读取 `clients.doc(clientId)`，校验实际 `id` 和 `tenantId`；领域层读取真实成员并比对 `membership.id === client.ownerMemberId`。clientId只是待验证资源标识，不能声明自己的权限。其他客户、其他企业、缺失或不存在的客户均不能借此越权。

**6. 当前开放账期负责人校验。** 云事务使用真实 membership.tenantId、已验证 clientId、`status: 'open'` 定向查询 `billing_periods`，最多读取2条来判断唯一性。结果替换对应客户的开放期快照片段；领域层沿用现有只读取已存账期的 `currentPriceOpenPeriod` 查询辅助函数，再使用独立创建权限判断。该辅助函数本身没有修改。不会使用前端 periodId，也不依赖通用快照的前1000条恰好包含授权记录。

**7. 历史负责人不授权。** `settled/closed` 记录不进入开放期查询；也不调用会合成旧账期的 `allPeriods` 来授权。“曾负责该客户”没有授权分支。没有开放期时，普通账期负责人不能创建，客户负责人和管理员仍可创建。

**8. 多开放期的处理。** 读到2条即不使用账期负责人分支，不选择其中任意一人。客户负责人和管理员分支独立，仍保留各自创建能力。测试也覆盖第2条开放期位于通用快照读取上限之外的情况。

**9. 负责人变化即时失效。** `mutate` 每次执行及事务冲突重试都从真实 OPENID 重新取得 active membership，再读取客户和开放期。客户转移、账期负责人转移、结清、下一期开启、成员停用/删除/换企业均按保存时状态决定；旧页面缓存的 true 不参与授权。失去客户身份但仍负责当前期，或失去账期身份但仍负责客户，均可继续创建。

**10. direct API 防伪。** 顶层、payload 和产品参数中的 tenantId/role/memberId/ownerMemberId/periodOwnerMemberId/isAdmin/canCreateCustomProduct/periodId 不作为授权来源。正式 tenant 从 OPENID 对应 membership 派生；当前成员注入事务快照，领域保存再次读取该真实成员。未登录、陌生微信、失效成员在入口被拒绝。服务端拒绝不写产品和审计。

**11. 修改/启停权限保持。** `updateCustomProduct`、`setCustomProductActive`、`setProductActive` 等继续经过原管理员门禁。本轮没有修改它们的领域函数。原创建函数遇重复产品会合并别名、关键词、标签并补齐结构字段；这是可被间接用于更新的路径。本轮普通成员遇重复仅返回原产品，任何字段、updatedAt和审计都不改。管理员原重复补充行为保留，并受底槽身份兼容检查约束。

**12. 企业共享模型保持。** 创建产品对象继续由明确字段白名单构造，只有 tenantId 企业归属；不写 clientId、ownerMemberId、periodOwnerMemberId、createdForClientId。请求和页面表单的 clientId 仅供授权，不是新增数据库字段。其他成员可以直接复用企业中已存在的底槽产品。

**13. 审计与内容安全。** 新建继续写 `CREATE_CUSTOM_PRODUCT`，保留原 after、createdAt、performedByMemberId、performedByNameSnapshot；新建原本没有 before，本轮不虚构。审计操作人来自服务端真实成员，不冒用管理员。产品名称、备注、别名、识别关键词等继续经过原 `collectChangedTextFields → assertTextContentSafe → msgSecCheck`，之后才持久化；风险文本会回滚产品与审计。重复纯复用不写新文本，沿用既有“仅检查发生变化文本”的规则。

## 三、底槽识别与复用

**14—15. 原因及降级位置。** 原 `services/order-parser.js` 的 `SPECIAL_PRODUCT_TAGS` 没有“底槽”。所以 `extractSpecialProductFeatures` 返回无特殊属性，`parseProductCandidate` 之后调用 `findProduct(height,width,toothType,color)`，仅凭40×25、细齿、灰色命中普通标准品。不是 `normalizeCustomProductName` 主动删除了“底槽”，而是匹配路径没有把它当作身份。另有两个潜在绕过：精确别名/关键词匹配原来不校验底槽边界；结构化特殊长度匹配原来可以仅凭相同长度返回。

**16. 新规则。** 只新增明确词“底槽”，沿用原 specialTags 和自定义产品结构，不增加同义词或语义推测。尺寸/颜色/齿型/长度函数从解析器提取为共享模块供解析与重复检测复用；原函数规则保持。“银灰色”仍归一为“灰色”。

```text
输入：银灰色细齿底槽4025 1.3米长 100根
产品身份：40×25 / 灰色 / 细齿 / specialTags=['底槽'] / unitLengthMeters=1.3
订单数量：100
订单单位：根
```

**17. 不会回退普通4025。** 明确底槽会设置 hasSpecialAttributes，先进入既有特殊匹配路径；普通标准产品不具有底槽标签，不能匹配。找不到符合完整身份的自定义产品时返回待人工确认/创建。建议名称也包含底槽。选择器按底槽身份分开列表，直接选择事件同样拒绝普通/底槽混用；用户在创建表单明确编辑并确认新底槽产品时，才采用该新身份。

**18. 普通4025不会误用底槽。** 所有自定义名称、aliases、recognitionKeywords 的候选先校验“是否底槽”一致；底槽产品即使含一个普通4025别名，也不能抢占普通输入。反向的普通产品底槽别名也不能让底槽输入降级。普通“银灰色细齿4025”仍正常匹配标准品。

**19. 已有产品复用。** 对底槽使用有序高宽、颜色、齿型、特殊标签集合及单根长度比较；词序、空格、常见分隔符变化可以复用同一个 ID。长度缺失和1.3米不同，1.2米和1.3米不同；40×25和25×40不同。普通成员重复创建不会更新已有产品；存在多个结构身份相同的底槽时，不任意重复创建，要求人工选择。

旧产品名称明确包含底槽但 specialTags 为空时，会在新输入匹配过程中只读提取该身份，不批量补写旧记录，也不重解释历史发货快照。

**20. normalized identity 区分。** `normalizeCustomProductName` 原函数保持不变；新的建议名称保留“底槽”，新产品 specialTags 也保留它。只有字段声明底槽而名称不含该词时，normalizedName补上底槽标记。词序等价判断通过结构属性完成，并非把所有词序强行改成相同名称字符串。订单数量从描述中剥离后才形成草稿，因此100米/100根不会进入产品身份。

**21. 其他特殊词。** 装潢、定尺、定制、非标、短料、加长、裁切、特殊均保留。底板、底座、槽底、无盖、开槽未新增为底槽同义词。底槽和原特殊标签同时出现时保留组合，并防止仅凭长度或某一个标签误复用。

**22. 标准产品。** `data/product-specs.js` 及云副本逐字节未改，66个规格事实、可选齿型、颜色、60个标准盖子和普通标准品规则保持。

**23. 特殊长度。** 原长度提取逻辑、长度表达归一和订单数量分离逻辑保持；底槽增加严格兼容边界。特殊长度只提供换算依据，是否换算仍由原人工确认和计价规则决定。
