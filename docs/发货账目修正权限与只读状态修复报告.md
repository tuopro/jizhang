## 1. “进行中”为何显示“已结清”

原详情页只有 `canEdit`，计算式是“管理员且账期未结清”；WXML 将修改按钮的 `wx:else` 直接显示为“该账期已结清，历史账单保持只读。”因此普通成员进入真实开放账期时，单纯因为没有修改权限，也会看到错误的已结清提示。

本次将状态分开：`isClosed` 来自实际关联账期，`canEdit` 来自开放状态及当前成员、客户负责人。开放期非负责人仍可查看详情，不显示修改按钮，也不显示历史提示。已结清期继续显示原历史只读文案。路由的 `readOnly/historical/canEdit/role` 不参与判断。

| 真实账期 | 当前身份 | 修改入口 | 历史只读提示 |
| --- | --- | --- | --- |
| open | active admin | 显示 | 不显示 |
| open | active 客户当前负责人 member | 显示 | 不显示 |
| open | 其它 member（包括仅为录入人、账期负责人） | 不显示 | 不显示 |
| closed / settled | admin 或 member | 不显示 | 显示 |
| 账期缺失或关联异常 | 任意身份 | 不显示 | 显示关联异常原因，不冒充已结清 |

## 4. 最终修改权限表达式

在 shipment、实际 client、实际 billing period 均属于服务端真实 tenant，且关联一致的前提下：

```js
membership.status === 'active' &&
billingPeriod.status === 'open' &&
(
  membership.role === 'admin' ||
  (membership.role === 'member' && membership.id === client.ownerMemberId)
)
```

不使用 `shipment.createdByMemberId`、历史负责人快照或 `billingPeriod.ownerMemberId` 授权修正。真实 role 缺失或异常时也不能回退成管理员。

## 5. 服务端如何确认 client owner

保留真实 `cloud.getWXContext().OPENID` 查 membership 的入口，以及 `status === active` 和 tenant 校验。`updateShipment` 进入最终事务后再次读取 membership；随后通过事务内 `where({ tenantId })` 读取实际 shipments、clients、billing_periods 和 memberships。

领域方法按 shipment ID 找到真实 shipment，校验其 tenantId；按该记录自己的 `shipment.clientId` 查真实客户，再按实际 periodId 找已存账期，核验账期 tenantId 和 clientId。最后将真实 active membership 的 ID 与数据库中客户当前 `ownerMemberId` 比较。

请求中的 `tenantId/memberId/role/ownerMemberId/canEdit/isOwner/readOnly/historical/clientId/periodId` 均不能改写这条授权链，客户与账期关联不会被请求重新指定。不存在或错配的账期不能通过旧 `allPeriods` 的合成 open 记录获得修正权限。

## 6. billing period owner 与其它权限

结清规则完全不变：`admin OR currentMember.id === billingPeriod.ownerMemberId`，同时保留有效成员、余额为零、人工确认、日期和历史校验。客户负责人如果不是账期负责人，仍不能结清。

客户删除、负责人转移、账期负责人调整、成员管理、产品、客户价格、企业、收款和邀请的原 action 权限保持原状。原修正流程中的 `saveAsDefault` 原本处于管理员入口保护下；现在 member 修正若伪造该标记，服务端会拒绝整笔保存，页面也关闭这项能力。管理员仍保留原默认价保存流程。

## 7. 客户负责人变化

客户从 A 转给 B 后，以保存时读取的 `client.ownerMemberId` 为准：A 失去修正权、B 获得修正权，管理员仍可修正开放账期。单独转移客户不会修改账期负责人，不回写已有 shipment、录入人或历史姓名快照。

## 8. 历史账单保护

沿用原领域 `isClosedPeriod`：真实状态为 `closed` 或 `settled` 都拒绝修正，管理员也不例外。`closedAt/settledAt` 仍是日期展示和历史信息，不代替原 status 规则；余额为零、自然月份变化也不会自动结清。

修正只接受实际 `open`，其它未知状态也拒绝。旧月份账期 ID 可照常使用；缺少显式 periodId 的旧发货只在现有兼容 ID 能匹配真实已存账期且关系合法时允许修正。完全缺失账期的异常记录拒绝写入，不自动建期，不静默迁移。

## 9. TOCTOU 与并发

编辑页进入时通过现有 bootstrap 重新加载身份和数据，但按钮只是交互提示。保存始终再次经过云函数最终事务中的身份、资源、开放状态及负责人校验，不缓存页面打开时的授权。

测试覆盖：页面打开及入口校验之后，客户转移、账期结清、membership 停用/删除/企业变化，保存全部拒绝。另通过本地数据库模拟事务读取后发生并发写入，触发冲突重试，证明重试回调继续读取最新身份和数据，旧权限无法提交。真实云数据库的并发行为尚未做线上实测，本轮没有部署。
